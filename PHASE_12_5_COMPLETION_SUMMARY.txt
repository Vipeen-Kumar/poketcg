DESIGN DECISIONS RATIONALE
================================================================================

1. REGISTRY-BASED DISPATCH (not if/else chains)
   → Scalable: Easy to add new contexts
   → Testable: Custom registries for testing
   → Maintainable: No central if/else to modify
   → Future-proof: Supports any number of resolvers

2. GENERIC RESOLVER DEFAULT
   → Backward compatible: Existing behavior unchanged
   → Safe: Returns first index for single-select contexts
   → Simple: Minimal logic for standard case
   → Extensible: Easy to override for specific contexts

3. PRIZE RESOLVER SPECIALIZATION
   → Validates constraints: Ensures SDK requirements met
   → Explicit errors: Clear messages for debugging
   → Defensive: Prevents invalid submissions
   → Focused: Only handles TO_PRIZE context

4. SEPARATION FROM DECISION ENGINE
   → DecisionEngine remains unaware of multi-selection
   → Rules continue to select single actions
   → SelectionResolver interprets selections for SDK
   → Clean layers: Each component has one responsibility

5. BASELINE AGENT INTEGRATION
   → Resolve after validation: Ensures action is legal first
   → Before ActionSelection: Last step before SDK submission
   → Optional registry: Can inject custom registry for testing
   → Minimal changes: Only adds resolve() call
